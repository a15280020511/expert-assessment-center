## 三、发现并修复的缺陷

### 严重级

1. **被拒绝票据占用语义指纹但不能重试**  
   修复：允许原 Issue 在 `EXECUTION_REJECTED` 后修正并受控重试；只被拒绝、从未接受的历史 Issue 不再污染新票据。

2. **语义路由可能形成隐藏第五次付费调用**  
   修复：`approved_budget.calls` 成为路由、3 专家、裁判和替换共享的总调用上限；`calls: 4` 明确禁止路由调用。

3. **Benchmark 返回数据但实际 0 个模型匹配**  
   根因：模型目录使用请求 ID/规范化 slug，Benchmark 使用 `model_permaslug`。  
   修复：按精确 permaslug、同厂商去日期 slug、唯一规范化显示名做保守映射；无法唯一确认时继续回退，不猜测。

4. **实际选择模型与候选审计的 selected 标记不一致**  
   根因：实际选择完成后，候选审计又用恢复后的旧席位规则重新计算。  
   修复：实际选择和候选审计在同一个能力政策上下文生成；每席实际模型必须是候选列表中唯一 selected 项，否则运行失败。

5. **最终 Artifact Manifest 未覆盖真正上传的所有文件**  
   修复：报告分片、模型历史和最终文件全部生成后，再刷新 Manifest。

6. **缺少 `OPENROUTER_API_KEY` 时 Issue 报拒绝，但 Job 可能显示成功**  
   修复：缺失 Secret 成为显式 Job failure，同时保留零模型调用证据。

### 高优先级

7. **证据目录中的关键词污染任务分类**  
   修复：路由只读取实质任务文本；证据继续完整提供给专家，但不参与领域路由。

8. **语义路由器低置信度结果仍被采用**  
   修复：设置最低语义置信度；低于阈值时保留付费调用审计，但退回确定性分类。

9. **普通能力标签 `financial modeling` 被误判为指定模型**  
   修复：只拦截明确模型家族或 `vendor/model` 精确形式；普通建模、仿真、风险模型等能力标签允许通过。

10. **路由能力画像只记录、不影响实际专家任务**  
    修复：能力画像写入三名专家的 mission，并用于补充安全、法律、医疗、供应链、公共政策、数学等领域。

11. **反证席可能选择风险匹配为零的模型**  
    修复：优先使用风险+领域专业池；若不足四个独立厂商，则使用风险池；仍不足才通用回退，并在选择原因中明确披露。

12. **非编程任务可能选择代码专用模型**  
    修复：当非代码专业池仍能保留四个独立厂商时，排除代码专用模型。

13. **裁判可能因隐藏推理消耗输出额度而截断**  
    修复：优先选择可限制推理预算或无隐藏推理的裁判；追加 4200 中文字符完整报告契约；截断仍必须标记为 partial。

14. **只有裁判调用前预算预估，没有调用后实际费用合规判断**  
    修复：汇总供应商实际费用；超出剩余硬上限时生成 `actual-cost-breach.json` 并判定失败，不得作为合规成功交付。

15. **模型历史 Artifact 成为不必要的硬依赖**  
    修复：列表、下载或 JSON 校验失败时回退空历史；生成 `history-restore.json` 披露状态。

### 中优先级

16. **字符串 evidence 被静默忽略**  
    修复：只接受带 `note` 的对象或证据数组；字符串明确拒绝。

17. **票据校验每次通常只显示一个错误**  
    修复：一次收集并返回所有可检测结构错误。

18. **网页 GPT、路由器、选模器和专家职责混杂**  
    修复：建立独立委托契约；网页 GPT 只提交与交付，路由器只分类，代码选具体模型，专家和裁判负责结论。

## 七、当前仍然存在的限制与技术债

### 1. Benchmark 覆盖不是 100%

当前只有 8/36 个稳定合格模型能与 OpenRouter Benchmark 唯一匹配，其余使用官方智能排名回退。系统已经显式披露，不影响硬门槛和预算，但“性价比优先”对回退模型不是严格的任务 Benchmark/美元，而是智能排名近似值/美元。

风险等级：中。  
建议：等待 OpenRouter 提供更稳定的永久 ID 映射，或在不猜测的前提下扩充经过测试的别名字典。

### 2. 专业适配依赖模型目录描述质量

部分高能力模型的 description 不包含足够专业关键词，因此核心/交叉席可能在专业池不足时回退通用强模型。现在会明确披露，不再伪装为专业命中。

风险等级：中。  
建议：未来优先使用可靠 Benchmark 的领域子分数，而不是不断扩充模型名称硬编码。

### 3. 专家输出仍可能截断

最终验收中 `xiaomi/mimo-v2.5` 达到 5000 token 上限，被保存为 `success_partial`。系统不会把它冒充完整回答，裁判也会看到状态，但无法保证所有供应商每次都完整结束。

风险等级：中。  
建议：复杂任务可批准第 6 次调用，为路由后保留一次替换；或进一步压缩专家输出契约。

### 4. 实际费用闸门是事后合规闸门

供应商通常在调用完成后才返回实际费用，所以系统无法撤销已经发生的超支。当前设计能保证超支不被标记为合规成功，并留下证据，但不能绝对阻止供应商计费误差导致的瞬时超限。

风险等级：低到中。  
建议：继续保留安全系数，并避免把费用上限设置得刚好等于估算值。

### 5. 公开仓库隐私

Issue 和裁判报告对任何人可见。当前系统已经提示，但无法从代码上阻止用户主动粘贴敏感信息。

风险等级：高（仅当用户提交敏感数据）。  
建议：涉及合同、个人资料、商业秘密和内部通信时必须改用私有仓库。

### 6. Web GPT 委托边界不是密码学强制

仓库能在票据、专家提示词和报告中声明 Web GPT 不得替代分析，但无法从 GitHub 代码层控制外部聊天模型在仓库之外说什么。

风险等级：低。  
控制方式：执行纪律、明确来源标注和用户监督。

### 7. 能力选择与候选审计使用受测试的导入期绑定

为了尽量不重写成熟执行器，`capability_selection.py` 在模块加载时绑定选择产物写入器。现有 CI 会检测绑定是否存在，且每个 GitHub Run 都是独立进程；但如果未来大幅修改 import 顺序，需要同步更新测试或改成显式依赖注入。

风险等级：低，属于技术债而非当前故障。

### 8. `semantic_success_validation_recovered` 为兼容状态

源路由校验曾把普通 `modeling` 能力误判为模型名，后置守卫已安全恢复并完成全部审计。当前功能正确，但状态名仍表明走过兼容路径。

风险等级：低。  
建议：未来维护时将显式模型名识别逻辑直接收敛到一个公共函数，删除兼容分支。

## 八、最终生产判断

### 已达到

- Web GPT 与 GitHub 分工明确；
- GitHub 是唯一专家执行中心；
- 语义理解与确定性模型选择分离；
- 路由调用、专家、裁判和替换共享统一调用与费用上限；
- 无隐藏模型调用；
- 动态能力画像进入实际专家提示词；
- 具体模型由代码确定；
- 实际模型、候选列表和供应商 resolved model 可相互核验；
- 报告、费用、运行状态和哈希可追溯；
- 普通故障有明确失败语义或安全降级；
- 全部修改经过自动 CI 和真实付费 E2E。

### 未承诺

- 绝对零故障；
- 所有模型都有 Benchmark；
- 每个专家永不截断；
- 第三方平台、GitHub 或 OpenRouter 永不变化；
- 公开仓库自动保护用户主动提交的敏感信息；
- 供应商实际费用永远与估算完全一致。

## 九、审计结论

**生产验收：PASS。**

当前系统已经从“网页 GPT 猜任务、代码关键词选模”的简单结构，升级为：

> **Web GPT 负责使用与交付，GitHub 代码负责安全和精确模型选择，低置信度时由受限语义路由器补充能力画像，3+1 专家团负责实质分析，全部调用和证据受统一预算、状态与哈希约束。**

剩余问题主要是第三方数据覆盖和模型输出不确定性，不再是票据死锁、隐藏调用、审计不一致或责任混乱等架构性故障。
