# 任务矩阵驱动的专家团全局选择器

## 结论

生产选择链固定为：

```text
任务文本与显式约束
→ 确定性任务参数化
→ 任务需求矩阵
→ 动态生成候选专家职责
→ 拉取 OpenRouter 实时模型目录与 Benchmark
→ 生成“模型 × 席位 × 精确参数”候选矩阵
→ Google OR-Tools CP-SAT 分层求解
→ 输出专家团、裁判、参数、成本与完整审计证据
```

选择器不再使用：

- 固定的简单/中等/复杂团队模式；
- 固定的 1+1、2+1、3+1、4+1 映射；
- 固定参数模板库作为决策入口；
- 历史模型表现账本；
- 速度、热度或使用量排名；
- OpenRouter 自动路由器或在线模型变体；
- 由语言模型直接选择具体模型 ID。

## 一、任务输入参数

任务正文自动生成以下矩阵字段：

### 1. 领域向量

- 主领域；
- 次级领域；
- 交叉领域强度；
- 各领域需求分数。

### 2. 认知操作向量

- 分析；
- 决策；
- 证据核验；
- 定量计算；
- 情景预测；
- 反证与风险；
- 工程实现；
- 创意表达；
- 综合裁决。

### 3. 风险与规模向量

- 复杂度；
- 高风险程度；
- 上下文压力；
- 领域数量；
- 证据、定量、预测、反证和实施需求强度。

### 4. 可选硬约束

任务正文可包含：

```xml
<expert-team-input>
{
  "budget_usd": 1.5,
  "min_experts": 1,
  "max_experts": 4,
  "strict_provider_diversity": true,
  "candidate_pool_per_seat": 16,
  "solver_timeout_seconds": 10,
  "quality_tolerance_pct": 2,
  "forbidden_models": [],
  "preferred_models": []
}
</expert-team-input>
```

这些字段是具体约束，不是“预算/价值/质量”固定模式。`preferred_models` 只是软偏好，不能覆盖能力、上下文、预算和任务覆盖硬约束。

## 二、OpenRouter 实时输入

每次任务只使用当前实时数据：

- 模型 ID 与提供方；
- OpenRouter 模型排序和 Benchmark；
- 输入、输出价格；
- 上下文长度；
- 最大输出能力；
- 支持参数；
- 输入输出模态；
- reasoning 能力；
- 到期状态；
- 描述中的领域能力；
- 是否属于直接模型、预览版、免费变体、Batch 或 Online 变体。

稳定性分只由当前目录元数据计算，不读取过去运行历史。

## 三、动态席位

系统先生成候选职责，而不是预先决定团队人数。候选席位可包括：

- 主领域主研；
- 次级领域独立专业席；
- 证据、定量与情景校准；
- 工程实现与可执行性；
- 创意与表达；
- 独立反证与风险；
- 综合裁判。

只有覆盖任务硬需求所必需的席位才会被激活。最终专家数量由 CP-SAT 解得，不由“任务模式”决定。

## 四、硬约束

- 每个激活席位恰好一个模型；
- 每个模型最多使用一次；
- 默认每个模型提供方最多使用一次；
- 裁判始终存在且与全部专家独立；
- 所有任务硬需求必须被至少一个专家席覆盖；
- 专家数量满足任务输入的上下限；
- 只使用智能排序前 50 的稳定直接模型；
- 上下文、输出、模态和价格信息必须完整；
- 高风险任务必须有独立反证能力；
- 显式预算不得突破；
- 禁止工具、插件、在线路由模型与 Batch-only 模型。

## 五、分层优化

采用三阶段词典序优化，不做单一加权平均：

1. 在全部硬约束下，最小化足够覆盖任务的专家人数；
2. 在最小充分团队中最大化实时质量；
3. 保留接近最优的质量底线，在质量底线内最小化预计调用成本。

实时质量由以下数据构成：

- Benchmark 能力；
- 领域匹配；
- 席位能力兼容；
- 当前目录稳定性；
- 性价比；
- 预计成本效率；
- 反证席的风险能力。

## 六、参数生成

参数不是从固定模板中选择，而是由任务矩阵为每个“模型 × 席位”实时生成：

- reasoning effort；
- temperature；
- verbosity；
- structured output；
- 预计输出 token，仅用于成本估算，不作为请求硬上限。

每组参数通过内容哈希得到 `generated-*` 标识，便于审计和复现。

## 七、产物

每次选择至少产生：

- `task-parameter-matrix.json`：任务拆分后的完整参数矩阵；
- `benchmark-market.json`：OpenRouter Benchmark 与别名解析证据；
- `team-optimization.json`：CP-SAT 状态、分层目标、约束、候选数和最终解；
- `model-selection.json`：实际专家、裁判与参数；
- `artifact-manifest.json`：产物完整性清单。

## 八、可借鉴但不直接照搬的路由思想

### 值得借鉴

- Sparse MoE：只激活完成任务所需的最少专家；
- Expert Choice：允许不同任务使用不同数量的专家；
- Gating score matrix：建立“任务需求 × 专家/模型能力”匹配矩阵；
- Load balancing：用模型和提供方去重避免集中依赖；
- FrugalGPT / RouteLLM：在质量约束内优化成本；
- RouterBench：必须用统一指标评估路由，不应只看单次案例。

### 不直接照搬

模型内部 MoE 路由是联合训练的 token 级门控，拥有梯度、隐藏状态和可学习专家；外部 OpenRouter 模型彼此独立，价格、上下文和提供方约束也不同。因此这里只借鉴稀疏激活、动态基数、能力矩阵和负载均衡原则，不复制 token-level top-k 路由算法。

未来只有在积累了足够、可审计、带标签的真实任务结果后，才适合增加 RouteLLM、上下文 bandit 或 learning-to-defer 作为需求评分器；这些学习式路由器仍不能替代 CP-SAT 的硬约束和最终全局求解。
